# Checkpoint library revision — 2026-11-03

Implements the approved Saves mockup with one shared Save / Load / Delete button size. The main page contains the library, Categories menu, multi-selection checkboxes, Up / Down actions and a Steam save-folder button using the same folder icon as Viewer. There is no checkpoint settings dialog, mode picker or Details control. The Tools button is hidden; the advanced implementation remains in the source.

Categories, category transfers and display order are persisted separately from authenticated archive manifests and checkpoint files. Existing categories are read from archive metadata, with persisted library assignments taking precedence. Move to… transfers one or several selected checkpoints to an existing or new category without changing the authenticated archive or its original slot. All checkpoints remain available in the All checkpoints view. The main campaign label in the Campaign column is Main. Bulk deletion validates and stages only explicitly selected token-named LAB Plus archive folders. A staging failure restores already-moved archives. Cleanup deletes the known files and empty directories without recursive traversal; game slots, PROFILE and Steam metadata are outside the deletion targets.

A read-only `status` request discovers the actual campaign slot through the native adapter without reading or writing save files. Manual pause is no longer required. Capture accepts both an entered level (engine state 2) and the loading prompt (state 1) with a valid campaign/player/slot. Engine loading and file replacement require state 2; a request made at the prompt waits for the player to continue using their configured control. Save queue/task guards remain enforced, including before entering the level. Busy queues and sharing violations reset a continuous 500 ms quiescence window; preparation times out after 30 seconds without installing files. Invalid pointers, ownership, patch or slot changes remain errors. The saved object is the latest completed disk checkpoint, not the current simulation state.

The first live loading-prompt attempt exposed that meathook's frame callback is suspended before level entry. Status and archival therefore also run from presentation, outside the Vulkan state lock. A shared nonblocking mutex serializes both execution paths, and separate polling clocks prevent presentation from starving engine work. Presentation is explicitly barred from prepare/reload/restore: it cannot replace game saves or call the engine loader. Steam reads keep cache/disk comparison and account/Cloud checks; thread-local API parameter storage is released on the presentation path as described in the [Steamworks API documentation](https://partner.steamgames.com/doc/api/steam_api#SteamAPI_ReleaseCurrentThreadMemory).

Status probes and other operations share a serialized per-process mailbox. A read-only `prepare` request waits for an entered level and idle save queues before the companion reads the target snapshot for a restore plan. The restore transaction repeats all runtime and target checks after staging. Archives can be restored into another occupied slot of the same campaign; owner, patch, source integrity, current-slot/runtime checks, Steam-cache/disk verification and original retention remain enforced. Different campaigns cannot be mixed. DLC availability and archive patch compatibility control Load, while Delete and category transfer remain available for selected archives even without a running game. Loading prompts use neutral instructions, independent of key bindings.

In the main menu there is no loaded destination slot, so Load stays disabled with an explicit destination-slot explanation. Compatible archives retain normal row styling there; unavailable DLC or a different patch still produce unavailable styling. Loading directly from the main menu is not implemented by this revision. A fixture covers this distinction so old compatible archives do not appear incompatible just because the player has not entered a slot.

## Last-save console command

`labplus_load_last_save` is a no-argument action registered with the existing audited console bridge. The companion validates the selected game PID and a fresh 32-character request token, refreshes native slot/build/account status and uses the same prepare/stage/restore flow as Load. It does not depend on the visible category, row selection, manual order or source slot. A persisted last-created ID is scoped by Steam account, exact patch and Main/TAG1/TAG2 family. Existing libraries migrate once from their newest compatible archive; new captures update the identity. Deletion intentionally keeps that identity, so an unavailable last archive reports an error instead of loading an older save. Full archive verification and staging repeat the file checks, including deletion races. Results return as bounded token/PID-matched text in the game console; text is never executed as an engine command.

Managed fixtures exercise migration, persistence, cross-slot selection, account/patch/campaign boundaries, corrupted archives, deletion during selection, deletion across reopen and new capture after deletion. The UI fixture runs a valid console load through status/prepare/restore, then deletes that exact latest archive and checks that the command reports failure without sending another restore. Native fixtures check no-argument registration, unpredictable response tokens, stale/foreign reply rejection and bounded single-line feedback parsing.

Live console acceptance on 2026-11-03: the user entered `labplus_load_last_save` in DOOM Eternal 1.1 and confirmed that the save loaded. The companion's token-scoped console result reported `ok` and the intended latest compatible archive. Missing/deleted/corrupt command cases were exercised in isolated fixtures, not by deleting the user's live archives. The packaged ZIP contains only the 30 runtime files and has no user archives, tracking state or logs.
